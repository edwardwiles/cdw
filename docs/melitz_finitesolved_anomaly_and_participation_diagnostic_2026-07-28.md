## Phase 3: was 1.510118e14 ever a valid finite optimum?

**No.** `melitz_origin_block_screen` (the exact, joint, D-block convex-hull LP feasibility
certificate -- stronger than the always-on single-column range screen, which is only a
*necessary*, not sufficient, test and is documented as such) was run directly on `theta_new`
and returned **`InfiniteDeltaCertified(column=12, kind=:origin_block)`** -- an exact proof
that `DeltaStar(theta_new) = +infinity`. The always-on range screen passed (as it must,
structurally: it only rejects a single column whose value range excludes zero; joint,
multi-column infeasibility of exactly the kind manifesting here is invisible to it by design
-- documented in `inner_screening.jl`'s own file header).

Supporting evidence that the reported `FiniteSolved` was a numerical artifact of an unbounded
pursuit, not a genuine optimum:
- `nStatus=-103` ("approximate/stalled," not `0` = genuine KKT-optimal convergence).
- `||x|| = 2.18e17` -- a physically nonsensical dual magnitude for a converged CC dual problem.
- An independent re-evaluation of `obj(x_recovered)` at the SAME `theta_new` reproduces
  `1.510118285974391e14` exactly -- a pure *internal self-consistency* check (the functor is
  deterministic), which does **not** by itself certify validity; it only rules out a
  transcription/rounding artifact in how the value was read out.

Mechanism: with `obj.lower_limit=-Inf`, weak duality (file header of `inner_screening.jl`)
guarantees `-f(zeta,lambda;G) <= Delta^*` for *every* dual point, so as `DeltaStar(theta_new)
= +infinity`, the dual functor is genuinely unbounded above along some direction, and KNITRO's
own interior-point/CG algorithm pursued it without the cap-based early stop that would
normally intervene once a certified lower bound crosses the cap. It did not converge in the
usual sense; it appears to have run until it hit its own internal numerical-progress
tolerance (producing `-103`, not `0`) at an astronomically large but still-finite-in-`Float64`
iterate, which the OLD, incomplete acceptance rule (`nStatus in (0,-100,-101,-103)`, with no
cross-check against `obj.lower_limit`) then accepted outright as a "genuine" solve.

**Table of the governing prompt's four candidate outcomes, decisively resolved:**

| outcome | verdict |
|---|---|
| A. evaluation_cap mode with lower_limit=-10 was active but FiniteSolved still returned | **NO** -- `lower_limit` was never `-10`; it was `-Inf` throughout |
| B. the diagnostic path silently used uncapped `:full_value` mode | **partially** -- effectively uncapped, but not via an explicit `:full_value` choice; via an unset default nobody chose |
| C. the cap was requested but did not flow into the low-level bundle | **YES -- this is the confirmed root cause**, traced to `build_melitz_psi_bundle_from_calibration`'s own `inner_solve_config=nothing` default |
| D. sentinel/sign-conversion/stale-cache artifact | **NO on its own terms** (the value is a genuine, reproducible functor output, not a sentinel or stale value) -- but the underlying point IS genuinely infinite (Phase 3), so the *classification* is exactly as invalid as outcome D describes, arrived at by mechanism C instead |

## Phase 5: hardened result invariants

Two additive changes to `melitz_classified_inner_solve` (`src/melitz/inner_screening.jl`),
both defense-in-depth, both verified against the existing test suite (no `@test_throws`
target added or removed):

1. **Accepted-status gate now mirrors the pre-existing `cc_algo/inner_loop_functions.jl:207`
   Ricardian precedent**, which this Melitz classifier had silently dropped half of:
   ```julia
   accepted = nStatus == 0 || (nStatus in (-100, -101, -103) && objSol >= obj.lower_limit)
   ```
   (previously: `accepted = nStatus in (0, -100, -101, -103)`, with no cross-check against the
   bundle's own cap at all). This alone would not have prevented THIS specific anomaly (`obj.
   lower_limit` was `-Inf`, so `objSol >= -Inf` is trivially true) -- it protects a
   *correctly-capped* bundle from an analogous future failure mode where an approximate/stalled
   status slips past a genuinely active cap.
2. **A loud, unconditional output invariant**, added immediately before `FiniteSolved` is
   constructed:
   ```julia
   @assert Delta_theta <= delta_evaluation_cap + max(1e-6, 1e-6*abs(delta_evaluation_cap)) (...)
   ```
   matching `FiniteSolved`'s OWN pre-existing docstring intent ("only `delta_evaluation_cap`
   ... CAN abort a solve before this point") and the established `build_melitz_cc_bundle`/
   `solve_melitz_finite_delta_bound` precedent of converting a silent footgun into an
   immediate, loud error. This is a **universal, single-choke-point fix**: it protects every
   caller of `melitz_classified_inner_solve` (Phase 6's audit table below) regardless of which
   upstream constructor built `obj`, closing the *output-facing* half of the anomaly for the
   whole codebase in one place, without touching any of the several vulnerable constructors
   individually.

Verified NOT to break the existing test suite's own deliberately-decoupled
`delta_evaluation_cap`-vs-`obj.lower_limit` test fixtures (e.g.
`test/melitz/runtests.jl:5865` builds an uncapped `obj` via `build_melitz_psi_bundle` and
calls `melitz_classified_inner_solve` with `delta_evaluation_cap=10.0`, but its own `theta0`
base point never approaches the cap, so neither new check fires) -- confirmed via a full
suite run (Phase 12/Acceptance Criteria below).

A regression test using the exact anomalous fixture (the reconstructed `theta_pt`/`theta_new`
pair and seeds from Phase 1) would require ~30-60s of real-D20 KNITRO wall time per run if
added to the routine suite; given this session's scope explicitly excludes "optimize marginal
code performance" and the suite is already large, the reconstruction script itself
(`scripts/melitz_anomaly_phase1_reconstruct_2026-07-28.jl`) is committed as the durable,
exact, deterministic repro artifact instead of a new `@testset` entry -- disclosed as a
scope trade-off, not an oversight.

## Phase 10: final interpretation

1. **How did 1.510118e14 arise?** A genuinely `InfiniteDeltaCertified` real-D20 point
   (Phase 3, proven by `melitz_origin_block_screen`) was solved by KNITRO with NO active
   evaluation cap (`obj.lower_limit=-KN_INFINITY`, Phase 2), so the dual iterate diverged
   chasing an unbounded objective and was accepted at an astronomically large but
   floating-point-finite iterate under a "stalled/approximate" status code (`nStatus=-103`,
   `||x||~2.2e17`) that the OLD acceptance rule treated identically to genuine convergence.
2. **Was the production evaluation cap active?** No. `delta_evaluation_cap=10.0` was passed to
   `melitz_classified_inner_solve`, but that argument only gates the pre-solve screens; the
   actual live KNITRO-native cap (`obj.lower_limit`) is fixed at bundle-construction time and
   was left at its silently-uncapped default by the shared fixture builder every 2026-07-27/
   07-28 phase script uses.
